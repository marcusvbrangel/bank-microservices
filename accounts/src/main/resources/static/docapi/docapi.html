Accounts API: tutorial blinda, killer e direto ao ponto

Este guia ensina a usar a API de contas com padrao profissional: fluxo completo, exemplos reais e boas praticas para produzir rapido, com seguranca e previsibilidade.

Base URL http://localhost:8081/api/v1/cards
Swagger UI /api/v1/swagger-ui.html
OpenAPI /api/v1/api-docs

Fluxo ideal (10 min)

  1. Suba o microservico accounts.
  2. Crie uma conta com POST.
  3. Guarde o accountNumber retornado.
  4. Consulte, atualize e delete.

Regras de dados

  • mobileNumber tem 10 digitos.
  • name entre 5 e 30 caracteres.
  • email valido e obrigatorio.
  • accountNumber tem 10 digitos.
Comece agora

Setup rapido e sem erro

Tudo o que voce precisa para ter a API rodando e testar em menos de 5 minutos.

1) Suba o microservico

No diretorio `accounts`, rode o Spring Boot (porta padrao 8081).

Terminal
cd accounts
./mvnw spring-boot:run

2) Configure o base URL

Guarde o endpoint principal para reutilizar nos exemplos.

Terminal
export ACCOUNTS_API="http://localhost:8081/api/v1/cards"
Observacao: o path da API esta configurado como /api/v1/cards no controller. Se voce alterou para /api/v1/accounts, ajuste o base URL nos exemplos.
Mapa da API

Endpoints principais

Quatro operacoes cobrem o ciclo completo de contas.

Metodo Path Uso Status
POST /api/v1/cards Cria cliente e conta (accountNumber gerado pelo servidor). 201, 409, 400, 500
GET /api/v1/cards/{mobileNumber} Busca dados completos pelo celular. 200, 404, 400, 500
PUT /api/v1/cards Atualiza cliente + conta usando accountNumber. 200, 404, 400, 500
DELETE /api/v1/cards/{mobileNumber} Remove conta e cliente pelo celular. 200, 404, 400, 500
Passo a passo

1) Criar conta (POST)

Envie apenas dados do cliente. A conta e criada com accountNumber e dados padrao.

Payload minimo

O servidor gera accountNumber, accountType e branchAddress.

JSON
{
  "name": "Santos Dumont",
  "email": "santos.dumont@gmail.com",
  "mobileNumber": "5524785214"
}

Requisicao

Use Content-Type application/json.

cURL
curl -i -X POST "$ACCOUNTS_API" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Santos Dumont",
    "email": "santos.dumont@gmail.com",
    "mobileNumber": "5524785214"
  }'

Resposta esperada

201 Created
{
  "statusCode": "201",
  "statusMessage": "Account created successfully"
}
O accountNumber e gerado aleatoriamente e o accountType padrao e "Savings". O branchAddress padrao e "123 Main Street, New York".
Passo a passo

2) Buscar conta (GET)

A consulta retorna cliente + conta. Use o mobileNumber (10 digitos).

Requisicao

cURL
curl -i "$ACCOUNTS_API/5524785214"

Resposta esperada

200 OK
{
  "name": "Santos Dumont",
  "email": "santos.dumont@gmail.com",
  "mobileNumber": "5524785214",
  "accountNumber": 1830572220,
  "accountType": "Savings",
  "branchAddress": "123 Main Street, New York"
}
Passo a passo

3) Atualizar conta (PUT)

Atualiza dados do cliente e da conta. Inclua accountNumber.

Payload completo

JSON
{
  "name": "Santos Dumont",
  "email": "s.dumont@wolfbank.io",
  "mobileNumber": "5524785214",
  "accountNumber": 1830572220,
  "accountType": "Savings",
  "branchAddress": "Avenida Central, 250"
}

Requisicao

cURL
curl -i -X PUT "$ACCOUNTS_API" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Santos Dumont",
    "email": "s.dumont@wolfbank.io",
    "mobileNumber": "5524785214",
    "accountNumber": 1830572220,
    "accountType": "Savings",
    "branchAddress": "Avenida Central, 250"
  }'

Resposta esperada

200 OK
{
  "statusCode": "200",
  "statusMessage": "Account updated successfully"
}
Passo a passo

4) Deletar conta (DELETE)

Remove conta e cliente pelo mobileNumber.

Requisicao

cURL
curl -i -X DELETE "$ACCOUNTS_API/5524785214"

Resposta esperada

200 OK
{
  "statusCode": "200",
  "statusMessage": "Account deleted successfully"
}
Modelo de dados

O que enviar e o que receber

Use este resumo para validar o payload antes de enviar.

CustomerDto

  • name: 5-30 caracteres.
  • email: formato valido.
  • mobileNumber: 10 digitos.

AccountDto

  • accountNumber: 10 digitos.
  • accountType: obrigatorio.
  • branchAddress: obrigatorio.

CustomerAccountDto

  • Todos os campos de CustomerDto.
  • Todos os campos de AccountDto.
Erros e validacao

Como lidar com falhas sem surpresa

A API retorna validacao detalhada e erros padrao de negocio.

400 - Erro de validacao

Exemplo
{
  "mobileNumber": "Mobile number must be 10 digits",
  "email": "Email should be a valid value"
}

404 / 409 / 500

Exemplo
{
  "apiPath": "uri=/api/v1/cards/5524785214",
  "statusCode": "NOT_FOUND",
  "errorMessage": "Wasn't possible to find a customer with the mobile number 5524785214",
  "timestamp": "2024-01-31T10:45:02.311"
}
409 acontece quando o mobileNumber ja existe. 404 quando nao encontra cliente ou conta. 500 cobre erros inesperados.
Nivel profissional

Boas praticas para produzir sem retrabalho

Use estas rotinas para evitar erros comuns em integracoes reais.

Checklist de integracao

  • Normalize o mobileNumber (somente 10 digitos).
  • Guarde o accountNumber do GET para updates.
  • Valide email no client para reduzir 400.
  • Trate 409 como conflito de cadastro.

Ambiente de desenvolvimento

  • Banco H2 em memoria: dados somem ao reiniciar.
  • Use Swagger UI para validar payloads rapidamente.
  • Versione exemplos no Postman para o time.
  • Reaproveite o base URL via variavel de ambiente.
Passo final

Pronto para producao

Se voce passou por esta lista, sua integracao esta pronta.

Logs

  • Guarde status e errorMessage no client.
  • Identifique o mobileNumber nos logs.

Resiliencia

  • Retry somente em 500 com backoff.
  • Nao repita POST se ja recebeu 201.

Observabilidade

  • Monitore 400/409 para melhoria de UX.
  • Crie alertas para 500 recorrente.
